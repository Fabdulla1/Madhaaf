# Kutchi Roots architecture decision record

**Status:** Accepted for the initial implementation, 19 October 2026. Revisit choices that require a configured Supabase or Vercel project before production launch.

## Context and decision

The starting workspace has no application, repository instructions, Git repository, or existing data model. Kutchi Roots needs an editorial website, a private genealogy workspace, a Mombasa Kutchi dictionary, and a history archive. The first release has one explicitly provisioned administrator, no public sign-up, and no authentic family or historical records to seed.

Use one **modular monolith**: Next.js App Router and strict TypeScript for web routes and server actions/route handlers; PostgreSQL in Supabase as the sole content source of truth; Supabase Auth for identity; Supabase Storage for media; Tailwind and accessible UI primitives for presentation. Organize application services by `auth`, `family`, `dictionary`, `history`, `media`, `admin`, and `shared`. UI components call domain services rather than embedding authorization or SQL. Database migrations are the schema authority. This avoids a premature network boundary while allowing each domain to have independent validation, data access, and tests.

The browser may receive the public Supabase URL and publishable key. It must never receive the service-role key or database credentials. Server code authenticates each request, checks the database role and record visibility, validates payloads, and executes mutations. PostgreSQL grants and row-level security (RLS) form a second enforcement layer. Every exposed table needs explicit grants and policies; an authenticated Supabase user is not automatically an administrator. Supabase's [RLS guidance](https://supabase.com/docs/guides/database/postgres/row-level-security) and [server-side Auth guidance](https://supabase.com/docs/guides/auth/server-side/creating-a-client?environment=route-handler&framework=nextjs) support this design.

## Identity, roles, and publication

- `auth.users` owns credentials and sessions. `app_users(user_id uuid primary key references auth.users, role)` records an explicit `admin` assignment; its default role is nonprivileged. Future `family_member` and `editor` roles need migrations and separate permissions. Never infer admin status from email address, client metadata, or being the first visitor.
- Disable public sign-up in Supabase configuration. Provision the first Auth user from the protected Supabase management console or a one-time server-side setup procedure, then grant `admin` through a privileged SQL migration/setup script after verifying the exact user UUID. The setup guide must be explicit and repeatable. Additional accounts require an admin invite flow later.
- `/admin/**` requires a valid refreshed session and `admin` role before rendering. Every write operation repeats the server-side role check. The login page supports email/password, logout, password visibility, and a non-enumerating reset response when email delivery is configured. Use Supabase-managed anti-abuse protections plus a rate limit at the login endpoint.
- Editable resources have `draft`, `published`, and `archived` states, `version bigint`, `created_at`, `updated_at`, `created_by`, `updated_by`, and optional `published_at`. `UPDATE ... WHERE id = ? AND version = ?` (or an equivalent RPC transaction) rejects stale forms. Archive is a soft state; purge is a separate privileged maintenance action.
- `editorial_revisions(id, entity_type, entity_id, version, snapshot jsonb, changed_by, changed_at)` stores recoverable snapshots. `audit_events` records actor, action, target, timestamp, and safe metadata for permission changes, publication, relationship changes, and media deletion. Keep audit data free of credentials and unnecessary private biography text.

## Relational model

All primary content IDs are stable UUIDs. Slugs and preferred spellings may change; they are presentation fields and must not be the only permanent link target. Use foreign keys, checks, indexes, and uniqueness constraints in migrations. Avoid hard deletion of referenced records.

| --- | --- |
| Genealogy | `family_members(id, preferred_name, life_status, birth_text, death_text, birth_place, short_bio, long_bio, visibility, editorial_status, version, …)`; `member_names(member_id, name, kind, sort_order)`; `member_places(member_id, place, period_text)`; `family_relationships(id, person_a_id, person_b_id, kind, parentage_kind, certainty, start_text, end_text, visibility, editorial_status, version, …)`. For parent-child links, `person_a_id` is parent and `person_b_id` child. For partnerships, store canonical UUID order so the reverse pair cannot duplicate it. | Dictionary | `lexemes(id, headword, preferred_form_id, part_of_speech, usage_notes, etymology_notes, orthography_version_id, editorial_status, version, …)`; `word_forms(id, lexeme_id, spelling, kind, orthography_version_id, sort_order)`; `senses(id, lexeme_id, gloss_en, definition_en, sort_order)`; `examples(id, sense_id, kutchi_text, english_text, sort_order)`; `lexeme_relations(from_id, to_id, relation_type)`; `speakers(id, display_name, consent_status, attribution_text)`; `recordings(id, lexeme_id, example_id nullable, speaker_id, media_asset_id, consent_status, …)`; `orthography_versions` and `orthography_rules`. Retain media asset rows while referenced. Replacement creates a new object/version before retiring the old one. |

### Genealogy invariants

Unknown dates stay unknown; approximate periods remain text plus optional sortable bounds, never fabricated exact dates. `life_status = unknown` receives living-person privacy treatment. A member has one canonical row even when visual layout duplicates a card. Relationships may be biological, adoptive, unknown, disputed, or unconfirmed. Multiple partnerships are allowed. No relationship is inferred from names. Before creating a member, search possible duplicates and offer explicit reuse.

A transaction that creates a person and relationship must validate endpoints, self-links, duplicate links, and ancestry cycles. A recursive CTE (or equivalent transactional service) checks whether the proposed parent is already a descendant of the child. Concurrent relationship writes must serialize or re-check within the database transaction so two simultaneous requests cannot jointly create a cycle. A database-side function is preferable when the mutation spans multiple statements. A partnership is not an ancestry edge. The explorer obtains only authorized members and authorized edges, so an edge cannot reveal a hidden person through name, count, or graph metadata.

### Dictionary identity and Wikibase export

Preserve the user-provided Draft 0.3 spellings exactly: `maa`, `bapa`, `paani`, `ghar`, `hadaa ach`, `ku'la`. They have the respective English meanings Mother, Father, Water, House, Come here, and Why, and must be labeled as user-provided examples rather than phonemically verified data. Preserve the provisional symbols `a`, `aa`, `n`, `(n)`, `l`, `'l`, `gh`, and `ch` as editable orthography content. Do not add invented verified vocabulary.

An export uses immutable lexeme UUIDs as external identity, word forms as written representations, senses as meaning records, examples as usage records, and source/speaker/recording provenance as referenced statements. Export version and orthography version travel with every record. This permits a future Wikibase Lexeme mapping without adding a second editable dictionary store. Keep a stable entry URL such as `/dictionary/<uuid>/<optional-readable-slug>` and redirect old readable slugs after edits.

## Visibility and media access

Genealogy is private by default. The initial RLS policy allows complete family access only to the admin role. Future approved family accounts need an explicit entitlement model, not a broad `authenticated` policy. A published dictionary entry or article is public only when its status and all referenced content satisfy publication rules. Public search and metadata queries must use the same predicates as detail pages. A public article may cite a private person only as non-linking editorial text after a separate consent decision; the application must never auto-resolve that citation to a private profile.

Keep all assets in the **private** `heritage-media` storage bucket. Issue a short-lived signed URL only after server-side authorization for the requesting user and asset; for a public article or dictionary entry, require the asset's explicit approval and consent plus an active published reference before signing. Do not persist signed URLs in public pages, cache keys, logs, or static metadata. Validate MIME type, actual file signature, byte size, file extension, and image/audio dimensions or duration as applicable. Use server-generated object paths, avoid executable file types, and record consent and attribution. Supabase documents that [private bucket downloads require authorization or a signed URL](https://supabase.com/docs/guides/storage/buckets/fundamentals).

## Routes, rendering, and interaction

The public site has `/`, `/dictionary`, `/dictionary/[id]`, `/orthography`, `/history`, `/history/[slug]`, and a privacy-conscious `/family` invitation/login state. The admin area has login and the eight requested sections: Overview, Family Members, Family Relationships, Dictionary, History and Culture, Media Library, Drafts and Publishing, Settings. Canonical person profiles and a graph explorer reside behind family authorization. Public content can be statically cached with targeted revalidation after publish/unpublish; authenticated genealogy and draft pages must be dynamic and private-cache only.

React Flow renders a zoomable, pannable genealogy projection. A layout module computes generational positions and can later use a dedicated graph layout engine without changing the database model. Search, focus, direct-neighbor highlighting, branch controls, reset, and touch navigation are application state. An HTML list/tree alternative exposes the same authorized people and relationships to keyboard and screen-reader users. Large graphs should load by branch or generation, with stable IDs and bounded response sizes. The canvas is a view of canonical data, never a separate editable graph store.

## Deployment, preservation, and recovery

Use separate local, preview, and production Supabase projects where practical; never point an untrusted preview at production private data. Environment variables include Supabase URL and publishable key for browser/server code and server-only management secrets only where a specific operation requires them. Keep production secrets in Vercel project settings. Apply migrations through a controlled release step before deploying code that depends on them. Set Auth redirect origins and storage policies per environment. Configure a real email provider before claiming password reset works.

Back up **both** PostgreSQL and storage objects. Database backups contain Storage metadata but not the underlying files, as [Supabase's backup documentation](https://supabase.com/docs/guides/platform/backups) states. Maintain encrypted off-project database exports and an independent, versioned copy of media objects plus a manifest containing paths, checksums, visibility, and consent metadata. Define retention and access owners in the deployment runbook; do not call the strategy verified until a restore to an isolated project has reconstructed database, buckets, policies, and sample private/public media. Export genealogy and dictionary in documented machine-readable formats on demand. Audit restore exercises and keep the last successful timestamp.

## Consequences and open operational decisions

The modular monolith keeps a single transaction boundary and one source of truth, but publication and media workflows require disciplined service boundaries and RLS testing. The first release can operate locally with Supabase CLI and a documented `.env.local`; production workflows remain unverified until credentials, Auth email delivery, storage buckets, and deployment projects exist. Before launch, decide retention intervals, legal basis and consent wording for living people and recordings, acceptable media size limits, public contribution contact path, and whether additional family accounts may view any subset of the tree.
