# UI critique — round 1

**Review state:** Public routes reviewed in a local production build on 19 October 2026. The administrator and family interfaces need a separate authenticated review once a configured Supabase environment and approved test records are available. No Impeccable skill or tool was installed, so this review follows the brief's Impeccable criteria: hierarchy, type, spacing, navigation, states, mobile use, accessibility, interaction, and cultural care.

## Evidence and method

- Inspected actual Playwright renders at desktop (1440 × 900), tablet (768 × 1024), and mobile (375 × 812). Production captures: [home desktop](screenshots/home-production-desktop.png), [home mobile](screenshots/home-production-mobile.png), [dictionary tablet](screenshots/dictionary-production-tablet.png), [dictionary mobile](screenshots/dictionary-production-mobile.png), [history mobile](screenshots/history-production-mobile.png), [orthography mobile](screenshots/orthography-production-mobile.png), and [mobile menu open](screenshots/menu-production-mobile.png).
- Checked route responses, browser exceptions, mobile menu state, and document width. Public routes /, /dictionary, /history, and /orthography returned HTTP 200 in the production build. No browser exceptions or horizontal overflow appeared at the measured widths; the menu-open state also stayed within 375 px after remediation.
- The Supabase environment is not configured locally, so public data panels correctly show unavailable states. Dictionary [list](screenshots/dictionary-fixture-mobile.png) and [exact-spelling search](screenshots/dictionary-exact-mobile.png) were separately inspected with only the six owner-supplied spellings and meanings as Playwright fixtures. This verifies presentation, not the live API or publication workflow.
- Reviewed source for content privacy and semantic controls. Screen-reader behavior, 200% zoom, touch tree gestures, audio, and authenticated editor flows remain to be tested in a configured environment.

## Findings

| ID | Severity | Location and observation | Resolution / evidence |
| --- | --- | --- | --- |
| UI-01 | Medium | Mobile navigation initially retained a “Menu” label after opening and its panel extended 3 px beyond the 375 px viewport. | **Resolved.** The summary now changes to “Close” and the panel aligns to the header edge. Production browser check returned menu text “Close” and document width 375 px; see [open menu](screenshots/menu-production-mobile.png). |
| UI-02 | Medium | Dictionary search placeholder was clipped by the submit button at 375 px. | **Resolved.** Changed the placeholder to “Word or meaning”; the [mobile dictionary capture](screenshots/dictionary-production-mobile.png) shows the full prompt. |
| UI-03 | High | The first dictionary API implementation capped browse results at 100, which would make A–Z navigation silently incomplete as the archive grows. | **Resolved in code; configured-data verification pending.** The API now supports letter, page, limit, and total/hasMore metadata. The public UI requests each letter and offers Previous/Next. A mocked API response displayed “Page 1 of 2” with a Next link to /dictionary?page=2. A real dataset over 24 entries is still needed for end-to-end confirmation. |
| UI-04 | Medium | Public navigation always showed “Admin sign in,” even for an authenticated administrator. | **Resolved in code; session verification pending.** The header now reads /api/auth/status and switches the desktop/mobile account link to Dashboard when admin is true. Playwright interception confirmed the Dashboard link in the mobile menu; live sign-in needs a configured account. |
| UI-05 | Medium | A later orthography version could have appeared above the hardcoded Draft 0.3 rule table, suggesting the old conventions belonged to the new version. | **Resolved in code.** The owner-supplied Draft 0.3 table now appears only for version 0.3 or while no published version is available; later versions use their published editorial guide. A future-version fixture review remains useful. |
| UI-06 | Medium | Public history articles need visible citations near the narrative to support the archive's evidence standard. The initial detail UI had categories and media but no source list. | **Resolved in code; configured-data verification pending.** The backend now supplies publication-safe source titles, citations, and URLs, and the article page renders a Sources section. Historical slugs also replace themselves with the canonical published slug. |
| UI-07 | Low | With Supabase unconfigured, the homepage repeated two identical “archive unavailable” panels. This honestly represented the environment but weakened the visitor path. | **Mitigated in code.** The dictionary and history states now name the affected content separately; the dictionary state links to the available writing guide. Reassess with published content after setup. The [initial home capture](screenshots/home-production-desktop.png) shows the prior generic copy. |

## Visual assessment

The public identity reads as a cultural archive: editorial serif headlines, a readable sans-serif interface, fine borders, warm paper, and an ocean teal illustration that is clearly decorative. The hero, introduction, language search, private family invitation, history, and footer form a coherent progression. No invented genealogy, archival photography, historical article, or extra Kutchi vocabulary appears. The mobile views preserve heading hierarchy and workable control sizes, and the private family invitation reveals no record data.

The current review cannot judge the final balance of dictionary entries, source citations, article images, or the family tree against real content. Those checks belong in the configured end-to-end review; a successful build and fixture render do not establish them.
